Playbook d'équipe Afrosite

Qui fait quoi, dans quel ordre, avec quel niveau de qualité — pour livrer un MVP avancé à trois : socle commun + 3 blueprints, pipeline IA gouverné, paiement Mobile Money en production.

Version 1.0 · 30 août 2026 Version complète docs/11-playbook-equipe.md Équipe Souraka · CHITOU · SERGE Horizon 90 jours → 5 pilotes Cotonou

Comment lire ce document. Il ne remplace pas la documentation projet : il la traduit en responsabilités et en tâches datées. En cas de contradiction, les docs numérotés font foi — signale l'écart dans le canal d'équipe et ouvre un ADR (§11). « Avancé » ne veut pas dire « plus de périmètre » : le périmètre reste 3 blueprints (doc 01 §5.4). L'avancé est dans la rigueur du pipeline — gates, agents, audit trail, streaming, boucle de critique visuelle, couche paiement multi-PSP, tolérance réseau.

Version canonique

Cette page est la vue d'ensemble. La version complète et versionnée dans le dépôt est docs/11-playbook-equipe.md — elle contient l'intégralité de la bibliothèque de prompts par rôle, l'arborescence détaillée et la liste exhaustive des branches. Les §15 à §17 ci-dessous en sont l'essentiel.

Réalité de l'effectif

Trois personnes ne couvrent pas nativement SRE, QA dédiée, MLOps ni sécurité offensive. Mitigations retenues :

1. Coolify + Compose maintient l'infra légère — pas de Kubernetes, Vault ni cluster GPU au MVP (doc 06 §2, 07).
2. QA = responsabilité partagée et outillée : Playwright bloquant en CI, pas de QA manuelle systématique.
3. Un audit sécurité externe est budgété avant l'activation des clés PSP en production (§12).
4. Toute tâche hors compétence de l'équipe passe en risque suivi (§13) avec une date de décision « on forme / on sous-traite / on reporte ».

Dépôts & open source sans perte de qualité

La consigne : réutiliser les briques qui existent déjà (doc 06 §2) sans hériter de leur dette ni casser la cohérence. La méthode tient en une phrase : on dépend des briques, on ne les fork pas, et on les isole toutes derrière une couche d'adaptation maison.

4.3 — Les 8 règles d'hygiène des dépendances

  1. Jamais latest. Versions épinglées (lockfiles committés) et images Docker par digest sha256:, pas par tag.
  2. Un fichier THIRDPARTY.md. Par brique : version, pourquoi on l'utilise, mainteneur interne nommé, cadence d'upgrade, checklist de test pré-upgrade, plan de sortie (par quoi on la remplace si elle meurt).
  3. Zéro fork du cœur. Un besoin non couvert → on contribue en amont ou on l'ajoute dans notre couche d'adaptation. Un fork local n'est autorisé qu'avec un ADR et une date de dé-fork.
  4. Un smoke test maison par brique critique, bloquant en CI : Temporal → un workflow paiement de bout en bout sur sandbox ; LiteLLM → un appel + un fallback simulé ; LangGraph → un graphe minimal avec reprise après échec.
  5. Renovate/Dependabot en PR groupées hebdo. Auto-merge autorisé seulement pour les patchs de dépendances non critiques qui passent toute la CI. Jamais d'auto-merge sur litellm, temporal, langgraph, SDK Genius Pay.
  6. Vendoring seulement pour un patch porté en amont (vendor/ + lien vers la PR upstream). Sinon, dépendance normale.
  7. Un README « golden path » par service : une seule commande pour lancer en local (docker compose up), une pour les tests, une pour les migrations. Si un nouveau contributeur ne démarre pas en 15 min, c'est un bug.
  8. Séparation stricte des rôles d'orchestration : Temporal pour tout ce qui touche l'argent et le provisioning ; LangGraph pour le raisonnement d'agents. On ne met jamais de logique de paiement dans un graphe d'agent.
Le vrai levier qualité

packages/contracts est la pièce la plus importante du dépôt. Le schéma Blueprint JSON y est défini une fois ; front (Zod) et back (Pydantic) en dérivent. Un validateur rejette tout JSON non conforme avant qu'un workflow démarre (doc 06 §5). Tant que la frontière est typée et testée, front et back peuvent avancer en parallèle sans se casser.

5

Le pipeline prompt → production

Chaque étage a un propriétaire et une gate à franchir (doc 06 §4-5, deep 04 §2B pour l'ajout Vision Critic). Rien ne passe à l'étage suivant tant que la gate n'est pas verte.

  • 01Prompt → Blueprint JSON — Intent Agent normalise, Product Architect structure. Gate 1 : schéma conforme, budget IA sous plafond, pas de donnée sensible.Souraka
  • 02Génération dans une branche Git — Code Agent (OpenHands SDK) en sandbox, jamais sur main. Gate 2 : lint/typecheck, tests unitaires, build, zéro secret.SERGE
  • 03Sécurité — Security Agent : SAST, scan dépendances/secrets, RBAC, rate limiting, CSRF/XSS/injection. Gate 3 bloquante.SERGE
  • 04Paiement — Payment Agent : sandbox Genius Pay, webhooks signés vérifiés, idempotency key, montants recalculés serveur. Gate 4.SERGE
  • 05Tests — QA Agent : unitaires + Playwright E2E. Gate 5 : migration testée sur copie, backup vérifié, rollback prêt.Souraka (A) · CHITOU/SERGE (R)
  • 06Preview déployée + capture d'écran automatique (Playwright).SERGE
  • 07Vision Critic Agent — lit la capture, évalue polish / cohérence / typographie contre des critères écrits. Score insuffisant → itération ciblée du Code Agent.CHITOU
  • 08Validation utilisateur — plan, coût estimé, état en direct, audit trail visibles (doc 06 §10).Souraka
  • 09Production — Gate 6 : confirmation explicite admin, déploiement progressif, monitoring actif, rollback automatique.SERGE

Streaming à chaque étage (deep 04 §2A) : l'interface montre l'étape en cours dès qu'elle démarre, pas seulement à la fin. TTFT < 500 ms est l'objectif perçu (deep 01 §3).

À ne pas faire pendant ces 90 jours

  • Ajouter un 4ᵉ blueprint avant d'avoir validé les 3 premiers.
  • Activer une clé PSP en production avant d'avoir testé webhooks, échecs et remboursements en sandbox.
  • Construire Kubernetes, Vault ou un cluster GPU.
  • Donner un accès IA illimité sur l'offre gratuite.
  • Pousser du code généré sur main sans branche + revue.
7

Paiement — Genius Pay

Décision d'équipe à consigner

Les docs 03 §5, 06 et 10 §F nomment KKiaPay / FedaPay / CinetPay. Décision : Genius Pay devient le PSP primaire du MVP (clés API + doc en main). Il s'intègre derrière la couche PaymentProvider pour que FedaPay/KKiaPay restent des fallback activables (routage multi-PSP prévu en Phase 2, doc 01 §5.2). Action Souraka : ouvrir un ADR et mettre à jour docs 03 §5, 06 §5-6, 10 §F pour cohérence.

7.1 — Ce qui ne change pas, quel que soit le PSP

  • Afrosite n'est jamais dépositaire de fonds. Couche d'orchestration au-dessus d'un acteur agréé BCEAO.
  • Aucune donnée de carte (PAN/CVV) ne transite ou n'est stockée chez nous — champs/pages hébergés du PSP uniquement.
  • La redirection navigateur ne prouve jamais le paiement. Seuls le webhook signé et la vérification serveur du statut le confirment.
  • Ledger interne immuable, distinct des flux réels. Réconciliation quotidienne : encaissé par canal (cash, MoMo, carte), impayés.

7.2 — La couche PaymentProvider (contrat maison)

Toute la logique métier parle à cette interface, jamais au SDK Genius Pay directement. Changer de PSP = une seule implémentation à écrire.

MéthodeRôleGarde-fous
createTransaction(order, idemKey)Crée la transaction côté serveur, renvoie une référence + URL/handle de checkoutMontant recalculé serveur depuis le panier ; idemKey obligatoire ; devise = XOF
verify(reference)Interroge le PSP pour le statut réelAppelé avant toute écriture « payé » ; jamais confiance au retour client
handleWebhook(payload, signature)Vérifie la signature, normalise l'événementRejet si signature invalide ; rejeu idempotent ; horloge tolérante
refund(reference, amount, reason)Remboursement total ou partielConfirmation admin explicite ; tracé dans l'audit trail
reconcile(dateRange)Rapproche transactions PSP ↔ ledger interneJob quotidien ; alerte si écart > 0

7.3 — Séquence d'un encaissement

  • 1Client valide le panier → API Afrosite crée une transaction serveur (montant recalculé, idemKey).services/api
  • 2Redirection vers la page / le SDK sécurisé de Genius Pay.apps/web
  • 3Client paie (MTN MoMo / Moov Money). Le navigateur revient — statut affiché « en attente ».apps/web
  • 4Webhook signé Genius Pay → workflow Temporal : vérifie signature, appelle verify(), écrit dans le ledger.services/workflows
  • 5Transaction marquée paiement confirmé · notification WhatsApp au gérant.services/workflows
  • 6Job de réconciliation du soir : PSP ↔ ledger, tout écart lève une alerte.services/workflows

7.4 — Checklist d'intégration (SERGE, à cocher avant Gate 4)

  • Clés sandbox et production stockées en secret (jamais en base, jamais dans un prompt, jamais côté client).
  • createTransaction recalcule le montant serveur ; le montant client est ignoré.
  • idemKey unique par tentative ; un rejeu renvoie la transaction existante, ne recrée rien.
  • Signature du webhook vérifiée avec le secret Genius Pay ; payload non signé rejeté et loggé.
  • Webhook idempotent : recevoir deux fois le même événement ne double pas l'écriture ledger.
  • Statut confirmé uniquement après verify() serveur — jamais sur le seul retour de redirection.
  • Cas testés en sandbox : succès, échec, expiration, double webhook, webhook en retard, remboursement total, remboursement partiel.
  • Réconciliation quotidienne implémentée ; écart PSP/ledger → alerte (Grafana OnCall / canal d'équipe).
  • Aucune donnée PAN/CVV dans les logs, la base, les traces ou Sentry (scrubbing vérifié).
  • Runbook « paiement bloqué » écrit : comment diagnostiquer, qui appeler chez Genius Pay, comment rembourser manuellement.
  • Passage prod = approbation explicite (doc 06 gate 6) + doc 07 : jamais avant tests sandbox complets.

Design system & critique visuelle

Propriétaire : CHITOU. La qualité visuelle ne vient pas d'un meilleur prompt mais d'une boucle générateur → critique avec vision réelle du rendu (deep 02).

8.1 — Structure (doc 06 §11)

DossierContenu
/foundationscolors, typography, spacing, shadows, motion
/tokenstokens.json, semantic-tokens.json — ex. --status-payment-confirmed, jamais une couleur directe
/componentsButton, Input, Card, DataTable, EmptyState, PaymentStatus, OrderStatus, Money
/patternsRestaurantDashboard, POSLayout, KitchenBoard, QRMenu, MobileCheckout
/rulesux-principles, accessibility, responsive, visual-identity

8.2 — Les 4 agents de conception

Product Agent (besoin) · UX Agent (parcours) · Art Director Agent (palette, ton, contraintes) · UI Critic Agent (rejet). Séparer la direction artistique de l'exécution — les mélanger produit le « design IA générique ».

8.3 — Critères de rejet écrits (charte doc 09 §3.4)

  • Dégradé violet/bleu par défaut, glassmorphism décoratif, carte à barre de couleur à gauche.
  • Polices hors marque (Inter, Roboto, Arial). Marque = Space Grotesk (titres, montants, stats) + IBM Plex Sans (interface, texte long).
  • Émoji comme icône fonctionnelle. Icônes au trait uniquement, grille 24 px, trait 1,75 px.
  • Vert utilisé ailleurs que pour le statut paiement confirmé.
  • Montants pas en chiffres tabulaires, ou en italique.
  • Dashboard sans priorité opérationnelle ; contraste < 4,5:1 ; cartes répétitives sans hiérarchie.
  • Photo de banque d'images corporate au lieu d'une personne réelle en activité.

8.4 — La boucle (ajout deep 04 §2B)

  • 1Code Agent génère l'écran à partir du design system (pas d'une page blanche).
  • 2Déploiement preview → capture d'écran automatique Playwright.
  • 3Vision Critic Agent lit l'image : polish visuel → cohérence → typographie (ordre de fréquence des défauts).
  • 4Score insuffisant → itération ciblée du Code Agent sur les points relevés, pas un « refais mieux » générique.
  • 5Score OK → validation utilisateur.

Boucle d'apprentissage : mesurer temps de tâche, abandon, erreurs, questions support → hypothèse UX → variante → A/B → décision documentée dans le design system.

9

Data, coûts IA & recherche

Propriétaire : Souraka. La compétitivité IA d'Afrosite ne vient pas du modèle mais de l'ingénierie produit autour (deep 04 §3) — c'est exactement ce qu'une petite équipe contrôle.

9.1 — Instrumenter dès le jour 1 (doc 02 §5)

  • Coût par génération / prompt (tokens IA), attribué au tenant.
  • Coût stockage + bande passante par projet actif.
  • Coût des environnements de preview.
  • Coût SMS / WhatsApp / email par notification.
  • Temps de support humain par ticket.
  • Frais PSP — jamais absorbés sans refacturation transparente.

Cible : marge brute ≥ 70 %. Client Business à 15 000 FCFA/mois → coût variable direct ≤ 4 500–6 000 FCFA/mois. Au-delà : basculer vers crédits additionnels, modèle plus léger, ou traitement asynchrone.

9.2 — Routage IA (doc 06 §9)

TâcheClasse de modèle
Classification d'intention, résumé, extraction, traduction, reformulation de menuModèle léger / peu coûteux
Architecture produit, plan complexe, débogage difficile, revue de codeModèle puissant (raisonnement étendu activé)
Composants, migrations, tests, APIs, correctionsModèle spécialisé code
Tâches répétitives + données sensibles (quand le volume le justifie)Modèle local / open source

Fallback via LiteLLM vers un second fournisseur ou un modèle local en cas d'échec. Décodage spéculatif : souvent déjà activé côté API — le vérifier, pas le réimplémenter.

9.3 — Eval harness

  • 30+ prompts réels par vertical (collectés en visites terrain), rejoués à chaque changement d'agent ou de modèle.
  • Scoring : conformité du Blueprint JSON, coût en crédits, temps prompt → preview, score Vision Critic, taux de passage des gates du premier coup.
  • Un changement de prompt ou de modèle qui fait régresser un indicateur clé est bloqué comme une régression de code.

9.4 — Cadence de recherche

Une demi-journée par semaine. Tenir à jour deeprecherche_important/ : toute nouvelle info qui contredit une décision d'archi ouvre un ADR. Sujets ouverts : PI-SPI (BCEAO, paiements instantanés interopérables), évolution des SDK d'agents de code, coûts d'inférence, KYC/AML UEMOA.

Qualité — Definition of Done

10.1 — DoD d'une PR

  • Lint + typecheck + build verts.
  • Tests unitaires sur la logique ajoutée ; tests E2E si un parcours utilisateur change.
  • Zéro secret (TruffleHog / scan CI). Aucune clé dans le code, les tests, les fixtures.
  • CodeQL + Semgrep sans nouvelle alerte haute.
  • Migration réversible et testée sur copie si le schéma change.
  • Pas de couleur/police hors design system ; tokens sémantiques utilisés.
  • Textes en français, orientés résultat, sans jargon (voix doc 09 §4.5).
  • Relue par une autre personne. PR < ~400 lignes si possible.
  • ADR joint si la PR change une décision d'architecture.

10.2 — DoD d'un blueprint

  • Socle commun identique en code aux deux autres blueprints ; seuls les modules spécifiques diffèrent (doc 01 §9).
  • SSR + Metadata API + sitemap par tenant + JSON-LD Schema.org + canonical auto (doc 08 §2).
  • Core Web Vitals : LCP ≤ 2,5 s, INP < 200 ms, CLS < 0,1 sur mobile 3G/4G.
  • Mode dégradé testé : coupure réseau → file locale → synchro différée.
  • Parcours paiement sandbox complet vert (les 8 cas du §7.4).
  • Export CSV (transactions, clients, ventes) sans support technique.
  • Résumé quotidien WhatsApp généré.
  • Score Vision Critic au-dessus du seuil ; passe la checklist de conformité charte (doc 09 §5).

10.3 — Go-live d'un pilote

  • Webhooks, remboursement et réconciliation testés en sandbox.
  • Audit sécurité externe passé (au moins pour le périmètre paiement).
  • Sauvegarde restaurée avec succès au moins une fois (pas seulement « le backup tourne »).
  • Rollback répété à blanc.
  • Monitoring + alertes paiement / base / déploiement actifs.
  • Formation de l'équipe du client faite ; canal WhatsApp de support ouvert.
  • Runbook incident accessible aux 3 membres.

Système de prompts

Un prompt qui va vite est un prompt qui n'oblige pas l'IA à deviner : il porte tout — contexte, objectif, fichiers exacts, contraintes, livrable, branche, Definition of Done, interdits. Bibliothèque complète par rôle (Souraka / CHITOU / SERGE + transverses) dans docs/11 §8.

16.1 — Bloc de contexte (en tête de CHAQUE prompt)

## CONTEXTE AFROSITE — ne jamais omettre
- Produit : plateforme AI-native création + paiement Mobile Money + exploitation
  pour TPE/PME au Bénin (UEMOA). Socle commun + 3 blueprints : Commerce, Restaurant,
  Services. Le socle est le produit, pas le vertical.
- Stack : Next.js + TS (front) · FastAPI + PostgreSQL + Redis (back) · LangGraph
  (agents) · Temporal (workflows argent/provisioning) · LiteLLM (routeur IA) ·
  Playwright (E2E) · Docker Compose + Coolify · GitHub Actions.
- Monorepo : apps/web · packages/{contracts,design-system,blueprints,llm} ·
  services/{api,agents,workflows} · infra/ · docs/adr/.
- Règles non négociables :
  1. Un prompt n'exécute jamais une action risquée directement (workflow testable,
     réversible, observé ; l'humain valide les actions importantes).
  2. 80 % composants éprouvés / 20 % génération contrôlée.
  3. Afrosite ne détient JAMAIS de fonds. PSP = Genius Pay via la couche
     PaymentProvider. Ledger interne ≠ flux réels. Jamais de PAN/CVV stockés.
  4. La redirection navigateur ne prouve pas un paiement : webhook signé + verify()
     serveur. Idempotency key partout. Montants recalculés serveur.
  5. Streaming systématique de chaque étape vers l'UI.
  6. FCFA & français natifs. Jamais d'USD affiché au client final.
  7. Jamais de push généré sur main : branche + PR + CI + gates.
  8. Tokens sémantiques du design system, jamais de couleur/police en dur.
     Vert (#1F7A53) UNIQUEMENT pour le statut « paiement confirmé ».
  9. Offline-tolerant : file locale + synchro différée pour commande et caisse.
- Marque : Space Grotesk (titres, montants — chiffres tabulaires, jamais d'italique)
  + IBM Plex Sans (interface). Terracotta #C1502E · Or #D89B3C · Charbon #211B17 ·
  Sable #F3E7D8.
- Docs de référence : docs/01 → docs/11 + deeprecherche_important/.
  En cas de doute : demander, ne pas inventer.

16.2 — Mode opératoire d'une tâche (de la carte au merge)

  1. Cadrer la carte Notion : objectif en une phrase, fichiers cibles exacts, contrat concerné, branche nommée, Gate cible, DoD copiée. Sinon → reste en Backlog.
  2. Créer la branche depuis main à jour : git switch -c <type>/<scope>-<slug>.
  3. Assembler le prompt : bloc de contexte + squelette + prompt de rôle. Coller le contenu réel des contrats et fichiers, pas leurs chemins.
  4. Faire réfléchir l'IA avant de coder : « liste tes hypothèses, les fichiers touchés, tes questions ; attends ma validation ». Puis « Vas-y ». Supprime 80 % des allers-retours.
  5. Travailler en petits incréments : un diff par sous-problème, revu au fil de l'eau. Refuser un patch géant.
  6. Vérifier en local : pnpm turbo lint typecheck test build (ou uv run …). Rien ne part en PR rouge.
  7. Ouvrir la PR : titre Conventional Commit, description = lien carte + Gate + DoD cochée + captures si UI. Squash-merge.
  8. Revue par une autre personne : CHITOU sur le visuel · SERGE sur argent/secrets/multi-tenant · Souraka sur contrat/archi front.
  9. Merger, supprimer la branche, carte en Fait. Coller le prompt final dans la carte ; s'il resservira, l'ajouter à la Bibliothèque.

16.4 — Anti-patterns à bannir

  • « Fais-moi le module commandes » sans coller le schéma, la liste des fichiers, les rôles RBAC.

  • « Améliore le design » → remplacer par les critères écrits du Vision Critic.
